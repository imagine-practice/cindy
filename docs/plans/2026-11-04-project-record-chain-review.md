# 项目记录链页面与交互评审稿

版本：D0.1；日期：2026-11-04；状态：待产品评审，未冻结、未实现。

本稿只定义拟议的产品页面、字段、关系和可观察行为，不规定数据库、API 或可执行路由，不修改现行群聊规则。所有退款情节、编号、规则和成果均为演示数据；不代表任何业务项目已经确定规则或发生交付。

依据：[统一项目管理计划](2026-11-04-unified-project-management.md)、[群聊规则](../product-rules/bot-group-chat.md)、[任务术语](../product-rules/task-and-conversation-naming.md)、[设计规范](../design-rules/DESIGN.md)、[开发工作流](../dev-rules/development-workflow.md)。本稿细化记录链，不替代原计划。

## 1. 本次评审要确认的结果

从一条群消息进入退款需求，能逐步找到决定、版本计划、工作项、实际执行、候选成果、独立验收、发布和反馈；从任一成果也能反向找到来源与受验版本。每一步显示当前状态、依据和下一责任人，不以模型回复代替真实完成状态。

### 原型与现状边界

- 已有试点提供项目任务观察与原生任务打开；不能据此声称下列项目管理页面已经存在。
- 本稿新增业务项目身份、需求与工作项等页面。存储、原生任务返回入口、群消息定位和双向关联的公开能力，需要实现前核验；缺口不得以私有 DB/IPC 绕行。
- “工作项”是本稿用于区分业务交付切片与原生 Session 任务的暂定术语。正式 UI/i18n 落地前按术语流程登记和裁决，本稿不修改术语库。
- 群内自主推进程度尚未产品定案。下文仅描述已经进入确定计划、且具备执行权限的工作；创建记录、关联群聊或保存草稿本身不派发任务。

## 2. 共同页面结构与记录规则

### 2.1 页面骨架

桌面正常宽度：顶部面包屑与标题；标题下为状态、修订和负责人；正文显示内容；侧栏显示来源、关联结果与下一步；活动记录放在次级区域。

窄屏：单列，依次为标题/状态、当前结果或阻塞、主操作、内容、关联记录、活动记录。关联侧栏变为可展开区域，不横向挤压正文。不依赖悬停才能发现操作。

内容卡遵循现有设计规范与组件，颜色走语义 token，浅深主题等价。主操作按当前阶段变化；删除、取消、历史版本等不与主操作争抢视觉重点。

### 2.2 通用字段

“必填”指达到该阶段需要具备，不要求用户创建草稿时一次填写完。

| 字段 | 展示与来源 | 更新规则 |
| --- | --- | --- |
| 所属项目 | 标题上方项目名称，可返回项目 | 稳定项目身份；不由目录名或群名替代 |
| 记录标题与短编号 | 标题旁，如“退款需求 · 需求-01” | 标题可改；链接不随标题变化 |
| 当前状态 | 标题下，加载/未知与业务状态分开 | 依据对应记录或实际回执更新，不解析聊天语气猜测 |
| 负责人、下一处理人 | 当前责任与下一步责任分别显示 | 变更留活动记录；角色不等于固定执行模型 |
| 修订 | 普通视图显示“当前修订”；历史视图显著显示版本 | 内容变更形成修订；旧结果不覆盖 |
| 来源与关联 | 显示记录名称、关系和对应版本 | 关系显式保存；禁止仅靠同名匹配 |
| 最近更新 | 时间与更新者/执行来源 | 区分人工修改、模型建议、实际工具回执 |
| 阻塞/待决提示 | 附加提示，含影响和解除条件 | 不覆盖原阶段；未知状态单独显示 |

ID、完整指纹、设备路径和原始回执放在“证据详情”，普通首屏只呈现可理解的版本名称与验证范围。截图与成果不包含无关账号、凭据或私聊内容。

### 2.3 关联数量与归属

- 一条需求可有多个来源消息，一条消息也可拆出多项明确不同的需求。重复整理先展示已有映射及拆分理由，不能一概禁止合法拆分，也不能重复创建相同需求。
- 一个决定可影响多条需求/工作项；一个需求可进入多个版本，但每个版本必须明确本次纳入的范围。
- 工作项有一个主项目，可关联多条该项目需求的明确修订；复杂跨项目依赖显式标注，不把不同项目的同名项合并。
- 一个工作项可以有多次执行尝试。首版一次执行尝试归属一个主工作项；执行中的 Worker 为该尝试的执行结构，不额外冒充业务工作项。
- 候选成果可汇合多个工作项；验收绑定明确候选与需求修订；发布绑定确定候选和环境，不链接“永远最新”的动态结果。
- 所有页面的关系区包含反向链接。群成员与项目参与者是不同权限集合，关联不自动扩权。

## 3. P0：项目入口与记录导航

入口：左侧“项目”→ 项目列表 → 项目详情。

项目详情一级导航：概览、需求与计划、工作看板、执行记录、交付与验收、项目设置。首版不另建一套聊天界面。

概览首屏显示：目标、当前里程碑、固定范围内已验收项数、执行中/受阻/待决数量、最近交付、下一步。不得将工作项数量比例解释为工时完成率。

项目创建只要求名称与目标，负责人可暂缺；开始执行前必须具备协调责任、范围和推进规则。无群聊、无代码任务时项目仍能存在。

## 4. P1：群消息来源与需求入口

### 首屏与字段

| 字段 | 要求 | 展示/来源 |
| --- | --- | --- |
| 群与话题 | 建立来源关系时必有 | 群名、话题名；保留真实来源标识 |
| 原消息 | 建立关系时必有 | 原消息可见片段、作者和时间；每次打开核对访问范围 |
| 所属项目 | 整理保存前必有 | 关联群的默认项目；需要改归属时显式选择有权限的项目 |
| 已关联记录 | 自动查询 | “已整理为：订单退款 · 需求-01”，可多项 |
| 整理摘要 | 保存草稿前必有 | 模型生成建议，允许编辑；与原文清楚区分 |

### 交互与跳转

- 消息菜单“整理为需求”打开预览抽屉：来源 → 项目 → 标题/问题摘要 → 已有关联提醒。
- “保存需求草稿”成功后回显需求卡，点击打开 P2，定位来源区域；不启动研发。
- 需求卡在主群只显示标题、阶段、下一步和入口；详细争论放关联话题。
- P2“查看原讨论”返回原群/话题并定位消息。没有定位能力时明确显示有限入口，不能跳到群尾后声称定位成功。
- 原消息编辑时标注“来源已更新”，展示可访问的差异；不直接改写已经冻结的需求。消息删除或失去权限时显示来源不可用，不借快照泄露被撤回内容。

## 5. P2：需求详情

布局：标题“订单退款 · 需求-01”；阶段与负责人；当前问题/下一步；正文标签“内容、验收标准、关联工作、历史”。侧栏显示来源、决定、纳入版本和最新交付。

| 字段 | 要求 | 更新与展示 |
| --- | --- | --- |
| 标题、用户问题、期望结果 | 草稿保存必有 | 草稿允许简短；不以实现方式替代用户目标 |
| 使用者与适用场景 | 进入计划前必有 | 如店员处理取消订单；内容仅为业务设计输入 |
| 本次范围、不包含范围 | 进入计划前必有 | 示例：首版全额退款；部分退款不纳入 |
| 业务规则与异常路径 | 进入计划前必有 | 待定项关联 P3，不把模型假设写成已决定 |
| 交互设计引用 | 涉及 UI 时就绪前必有 | 指向明确设计修订，含正常/加载/空/错误/恢复 |
| 验收条件 | 就绪前必有 | 编号、前置条件、操作、预期结果、适用环境 |
| 优先级与理由 | 排期时必有 | 决策依据可追溯；不靠数字自动推导业务价值 |
| 产品负责人、独立验收责任 | 就绪前必有 | 可先指定角色，派发时落实到实际执行者 |
| 修订、来源、相关决定 | 系统维护 | 当前修订与各执行绑定的修订同时可见 |

状态：待澄清 → 待排期 → 计划内 → 实施中 → 待验收 → 待交付 → 已交付；已取消为独立终止状态。受阻是附加提示。多工作项时给出分项依据，不因其中一个结束而跳到待交付。

主操作：待澄清“补充需求”；待排期“纳入计划”；实施中“查看工作项”；待验收“查看验收”；已交付“打开交付入口”。可修改内容与可启动执行是不同权限。

需求改动打开影响预览：受影响工作项、在途执行、候选与已有验收。保存新修订不静默改变在途任务包；由协调者决定追加指令、暂停相关项或留到后续版本，操作均留记录。

## 6. P3：业务决定详情与群内待决卡

群卡：问题 → 为何需要决定 → 影响哪些工作 → 选项摘要 → 查看决定。项目页中为“待决事项”抽屉，保留完整依据。

| 字段 | 要求 | 说明 |
| --- | --- | --- |
| 问题、决定范围 | 创建必有 | 示例：开始制作后的订单是否进入自动退款 |
| 选项与影响 | 提交决定前必有 | 产品影响、技术影响和仍未知之处分开 |
| 提出人、应决定者 | 创建/处理前必有 | 业务责任人或规则明确授权者，不默认群内任何发言都可裁决 |
| 关联需求修订与工作项 | 必有至少一个 | 显示哪些工作真的被阻塞 |
| 最终结论、理由、决定者、时间 | 解决时必有 | 可由合法决定自动落账，不要求复制粘贴两次 |
| 被替代的旧决定 | 修改决定时必有 | 保留历史，新的结论明确生效范围 |

状态：待决定、已解决、已撤回、已被替代。决定解决后进入需求更新/条件复核；不能不检查依赖就强制恢复全部执行。群里附来源的结论与项目决定页引用同一记录。

## 7. P4：里程碑与版本计划

布局：目标与目标日期；“本次范围”列表；依赖和资源提示；待确定事项；已纳入/已移出范围历史。

| 字段 | 要求 | 说明 |
| --- | --- | --- |
| 名称、交付目标、协调负责人 | 建立计划必有 | 里程碑可跨多个发布版本；不与发布记录混用 |
| 需求及纳入修订/范围 | 开始执行前必有 | 同需求多版本需明确各自切片 |
| 必须验收条件 | 开始执行前必有 | 项目当前范围是否交付由这些条件决定 |
| 优先级与依赖 | 派发前必有 | 含跨项目/共享环境依赖；缺资源只阻塞相关工作 |
| 目标日期 | 可选 | 标为目标而非保证；无依据不自动填精确预计完成日期 |
| 范围版本 | 系统维护 | 新增/移出需求生成变更记录，不能暗改统计分母 |
| 发布要求、目标环境 | 涉及发布时必有 | 技术验收、业务接受和发布要求分别列出 |

“纳入需求”从 P2进入并回显计划；点击计划行回 P2对应范围。选择“拆解工作”先产生 P5建议包，达到就绪条件才进入派发。首次开启推进明确规则，已确定范围内不为普通技术决定逐项增加确认门。

## 8. P5：工作项与上下文交接

首屏：工作项标题/阶段、当前责任人、下一动作；阻塞卡优先；正文分“目标与上下文、依赖、执行、交付、验收”。

| 字段 | 要求 | 说明 |
| --- | --- | --- |
| 目标、交付物、需求修订引用 | 创建必有 | 示例“退款接口”，不能只有模糊标题 |
| 必读资料与设计/接口修订 | 就绪前必有 | 每项有用途与准确来源；关键输入缺失时阻止该项就绪 |
| 允许修改范围、禁止触碰范围 | 代码执行前必有 | 绑定仓库与相关约束；实际工作区在执行记录中确认 |
| 前置依赖与解除条件 | 就绪前必有，可明确无依赖 | 与共享环境占用区别展示 |
| 实现负责人、独立审查者 | 派发前必有 | 原作者不能充当自己的独立验收者 |
| 开发指导、自测与验收方法 | 就绪前必有 | 可操作的输入、步骤、预期与证据要求 |
| 执行模型策略 | 派发前必有 | 使用项目默认或任务覆盖；实际模型另由运行回执记录 |
| 当前执行与历次尝试 | 系统维护 | 失败重试保持原工作项，不能丢失前次成果与失败 |

状态：待准备、就绪、执行中、待验收、待修复、已验收、已取消；阻塞附加原阶段与原因。创建/派发中的未知回执显示单独的“执行状态待核对”，不冒充已启动或失败。

主操作：“补齐上下文”“开始执行”“打开当前任务”“查看验收”“查看交付”，依阶段和权限变化。派发记录稳定请求身份；点击失败或超时先查原回执，不能换请求重新启动。

## 9. P6：实际执行与原生任务

项目“执行记录”展示可扫描列表：工作项、尝试、实际任务、运行状态、执行者/实际模型、开始/结束时间、结果摘要、下一步。点击“打开任务”进入已有原生任务，不复制一套聊天时间线。

| 字段 | 要求 | 展示边界 |
| --- | --- | --- |
| 工作项、任务 ID、运行/尝试标识 | 接收实际回执后必有 | 同名任务依 ID 打开；还未有回执时不伪造 ID |
| 实际模型、执行设备/位置 | 回执可得时展示 | 未报告则显示未知，不从角色名推断；敏感路径受权限约束 |
| 需求/设计/任务包修订、代码基线 | 代码执行前必核对 | 未提交输入另有指纹；不能只用 commit 代替所有内容 |
| 目录、分支、写入范围 | 适用时必有 | 放执行详情，普通项目概览不堆技术字段 |
| 执行状态与时间 | 从宿主读取 | 不把原生 active、运行结束解释为业务已验收 |
| 自测、输出、异常与交接摘要 | 交付时必有 | 作者声明与实际可核验证据分开 |
| 停止请求与实际停止 | 发生时分别显示 | 等待确认期间不宣称已停，不抢占仍在写入的工作区 |

原生任务提供回到工作项的上下文入口是目标体验，需核对宿主扩展能力。若首版不能嵌入，保留原项目页面的位置与返回导航，并明示差异，不能伪造已有返回按钮。

## 10. P7：候选成果详情

首屏：“退款候选 B · 待验收”，突出可打开的预览/文件/部署入口和适用环境，随后列变更摘要、包含范围、自测与已知限制。

| 字段 | 要求 | 说明 |
| --- | --- | --- |
| 候选名称、不可变版本身份 | 提交验收必有 | 版本名给人读，指纹/commit/构建身份用于核对 |
| 组成工作项与执行尝试 | 必有 | 汇合多个实现，不能只链接最新一条任务 |
| 实现范围、设计/需求修订 | 必有 | 明确实现了什么、不包含什么 |
| 成果入口与环境 | 必有或明确缺失 | 地址、文件或构建包存在不等于可用；区分演示/测试/生产 |
| 作者自测及已知限制 | 必有 | 不当独立验收结论 |
| 相对前候选的变化 | 返工提交必有 | 帮助独立质量判断复验范围 |

更新候选生成 B，不覆盖 A。主操作“打开成果”“送独立验收”；源文件/中间产物列在次级区域，不混入可交付结果。

## 11. P8：独立验收与缺陷

首屏先给结论及范围：通过、部分通过、未通过或未执行；绑定需求修订、候选与环境。AC矩阵列“预期、实际、证据、未覆盖”。

| 字段 | 要求 | 说明 |
| --- | --- | --- |
| 候选身份、需求/设计修订、验收标准版本 | 开验前必有 | 默认打开受验历史版本，提供“与当前版本比较” |
| 独立验证者、时间、环境 | 必有 | 模拟、浏览器、真实客户端等方式清楚区分 |
| 每条条件的结果与证据 | 判定时必有 | 跳过/未执行不算通过；证据引用必须可核验 |
| 缺陷清单 | 失败时必有 | 复现步骤、预期/实际、受影响范围、归属、原候选、修后候选、复验 |
| 结论、覆盖范围、剩余风险 | 必有 | 不用一个绿色标记遮住未覆盖的重要路径 |
| 业务接受记录 | 项目要求时提供 | 与技术验收分开；普通技术项不额外等待人工确认 |

“退回修复”关联原工作项与原作者；“查看受验成果”打开 P7固定候选；“查看需求标准”打开 P2对应修订。缺陷只有复验依据充分时关闭，作者回复不直接关闭。

需求或成果变化后，显示“原结论适用于候选 A；当前 B 的这些条件待复验”。保留旧通过，不把它改成历史失败，也不自动继承到新候选。

## 12. P9：发布、交付与真实入口

首屏：“版本 B · 测试环境已验证 / 生产待发布”等准确状态，显示适用对象、交付内容和下一步。发布状态单独为待安排、待确认、发布中、结果待核对、成功、失败、已回退；确认是否需要由项目已有授权与发布规则决定。

| 字段 | 要求 | 说明 |
| --- | --- | --- |
| 发布版本与固定候选 | 发布前必有 | 不能在验收后悄悄替换包 |
| 目标环境、影响范围、执行负责人 | 发布前必有 | 本机测试窗口与日常安装版分清 |
| 验收及适用业务接受 | 发布前按项目规则核对 | 缺少必要验收显示具体缺口，不用安装成功替代 |
| 执行安排、授权依据、回退方式 | 按实际风险必有 | 当前已有依据直接沿用，缺少时只请求必要决定 |
| 实际发布回执与运行身份 | 完成时必有 | 命令成功与目标版本运行分别核验 |
| 实际入口、使用步骤、适用限制 | 交付时必有 | 自定义协议/桌面入口不伪装成独立网页 |
| 交付核验、通知状态 | 完成时分别记录 | 发布成功但群通知失败只重试通知 |

群内交付卡从这条记录生成：结果、实际入口、主要变化、限制、验收链接、反馈入口。只有适用范围确已交付才使用“已交付”；一项需求交付不会自动结束项目。

## 13. P10：使用反馈与闭环

入口：群中引用交付卡反馈，或 P9“反馈问题”。首屏显示“针对哪个版本、哪个环境”的可编辑上下文，而非再次要求用户回忆所有信息。

| 字段 | 要求 | 说明 |
| --- | --- | --- |
| 反馈内容、来源 | 创建必有 | 人工描述优先；模型分类只是建议 |
| 涉及需求/交付版本/环境 | 可确定时必有 | 无法确定显示待核对，不默认当前最新版 |
| 类型 | 处理时确定 | 已有约定不符合、范围外新需求、使用咨询 |
| 复现与期望 | 缺陷进入处理前补齐 | 不要求用户先懂技术；伙伴负责帮助澄清 |
| 归属及处理记录 | 处理时必有 | 老问题去重/关联，新范围创建需求，不静默扩大版本 |
| 解决依据与回访 | 关闭时必有 | 修复对应版本和验证结果；是否人工接受按项目条件 |

“原规则下退款结果不对”进入原需求下的缺陷；“希望部分退款”进入新需求或明确范围变更。原交付记录保留，新增反馈不抹掉历史验收。

## 15. 全链异常与状态一致性

| 场景 | 用户看到什么 | 处理约束 |
| --- | --- | --- |
| 保存中/离线 | 正在保存或尚未保存，本地输入保留 | 未有回执不显示已保存；是否支持离线草稿需能力核验 |
| 保存/派发超时 | 结果待核对、最后确认时间 | 查询同一操作身份，不换键重新派发 |
| 两人编辑同一需求 | 最新修订与冲突内容 | 不覆盖对方修改，用户/协调者合并后再存 |
| 群关联改变 | 新旧项目及生效边界 | 历史需求保持原归属，不复制执行或重新派发 |
| 群权限失效 | 来源或通知不可用 | 重新检查访问与执行授权；群所属执行遵守现行生命周期，不假定全部项目执行必须停止或继续 |
| 输入/设计修订改变 | 受影响项需核对，旧修订可查看 | 仅暂停依赖新决定的工作；向在途任务传递变更有真实回执 |
| 执行失败/机器离线 | 实际失败或状态未知，保留已有成果 | 未证实停止前不让另一执行者抢同一写入资源 |
| 证据缺失/打不开 | 该条件待验证及具体缺口 | 不用文件名、作者自述、截图存在替代验收 |
| 发布失败/结果未知 | 与技术验收分开的发布状态 | 按原发布记录对账/恢复，不重复执行已发生动作 |
| 通知失败 | 项目结果已记录，通知待恢复 | 重试消息不重做业务工作；重复投递可识别 |

## 16. 可评审场景与预期

| 编号 | 评审操作 | 应看到的结果 |
| --- | --- | --- |
| RV-01 | 从群退款消息整理草稿，再次整理 | 找到已有需求；必要拆分有明确不同范围 |
| RV-02 | 从需求打开原讨论并返回 | 定位原消息，返回仍在原需求修订与位置 |
| RV-03 | 尚未确定制作后退款规则 | 待决事项清楚显示影响；不提前让研发猜规则 |
| RV-04 | 需求纳入计划后拆成接口/页面 | 共享契约依赖可见；无依赖项可并发 |
| RV-05 | 打开两条同标题执行任务 | 通过稳定身份进入正确原生任务 |
| RV-06 | 作者交付候选A，质量判失败 | 工作项待修复；自测通过不覆盖质量失败 |
| RV-07 | 交付候选B并复验 | A旧证据保留；B结论绑定B及正确需求修订 |
| RV-08 | 验收通过后业务规则变化 | 显示需复验范围；不全量清空也不盲目继承 |
| RV-09 | 发布命令成功但入口打不开 | 交付核验未通过，不能生成成功交付卡 |
| RV-10 | 发布成功但群通知超时 | 项目发布结果不回退；仅通知待核对 |
| RV-11 | 交付卡提出部分退款 | 进入新需求/范围变更，不暗改原交付范围 |
| RV-12 | 群成员无成果访问权 | 可见信息符合权限；关联本身不授予访问权 |
| RV-13 | 窄屏/键盘打开历史验收并返回 | 状态与版本清晰、焦点合理恢复、不横向滚动 |

## 17. 评审决定清单与实施前缺口

| 决定 | 本稿建议 | 状态 |
| --- | --- | --- |
| 群内推进程度 | 已确定计划内自主推进，新范围/业务分歧进入待决 | 待产品决定，不能当现行授权 |
| 新消息是否自动生成需求 | 显式整理入口可用；自动识别先给建议，避免把闲聊全变任务 | 待产品决定 |

| 双向导航 | 项目页与原生任务/群消息能往返定位 | 需核对公开能力，缺口单列 |
| 业务完成判定 | 依据固定范围内的适用验收/接受/交付条件 | 评审建议 |

实施前核验：持久项目存储和修订/并发写入；消息定位与权限；原生任务关联与返回；成果引用及访问；关闭面板后的项目推进；公开事件/回执恢复；群关系变更与授权生命周期。不得用当前只读观察试点推断这些能力已可用。

下一阶段先评审页面/字段/关系，再由产品与技术伙伴冻结任务包、独立质量形成反例，执行伙伴实现；本稿不派发开发、不改现行配置、不创建业务数据。
