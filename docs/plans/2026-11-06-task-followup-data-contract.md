# Task follow-up request ledger v1 (frozen target contract)

This contract and its SQL fixture are the data-author handoff, not a production migration. No migration number is reserved here. The fixture is `apps/desktop/src/main/localDb/worker/opHandlers/__tests__/fixtures/botTaskFollowupRequests.sql`.

Owner scope is the existing owner database. Within it the primary identity is `(task_id, requester_bot_id, key_digest)`. `requester_bot_id` comes from the real resolved caller and owned task, never public raw input. Changing parent/canonical session or run does not change this scope. Group/thread access is still independently checked on every service call, including replay.

`key_digest = SHA256(raw idempotencyKey)`; `body_digest = SHA256(text.trim())`. No punctuation stripping, truncation, body-based deduplication or caller-session component. `input_id` is the stable existing delegation-interjection prefix plus a digest of `[taskId, requesterBotId, rawKey]`, without run suffix. It is globally unique within this owner DB. Main generates these values. Renderer/tools cannot supply trusted scope, phase, result, time or input ID.

Columns and constraints are exactly in the fixture. `admitted_run_sequence` and `child_session_id` record the admission, not the task's mutable current parent. The ledger survives snapshot replacement, pause, cancel, terminal state and restore. It is removed only when the task itself is deleted (FK cascade). No pruning of reusable keys is introduced.

Phases: `admitted` means a durable request plus fixed input identity exists; `dispatching` means the host has claimed dispatch and may have crossed its boundary; `unknown` preserves an uncertain dispatch outcome; `settled` has the actual public result in `result_json`. `native_accepted_at` records the existing native onAccepted callback (not message persistence, provider network consumption or model usage). A queued public result may be settled before later native acceptance; these facts remain separate. A lost ACK must never cause a second input ID or blind repeat dispatch.

Internal named transaction `bots.followupRequest` supports scoped lookup, lookup by run/input, atomic admission, dispatch claim, native-acceptance annotation, uncertain outcome and final result. Admission requires `expectedRunSequence >= 1`. Lookup of an existing successful key recognizes its original admitted run regardless of the task's current run; conflicting body is rejected. Only a new key compares the exact expected run with current run. Terminal admission calls the existing reopen core and inserts the ledger in the same SQLite transaction; errors roll back both. Active admission only records the fixed original interjection input. Existing `bots.reopenDelegation` also gains mandatory expectedRunSequence so stale unkeyed transaction replay cannot pass status ABA.

The service returns the exact persisted public result for known replay, or explicit `FOLLOWUP_PENDING` / `FOLLOWUP_OUTCOME_UNKNOWN` without dispatch. It rechecks real caller/group permissions first and after storage awaits. No ordinary message approves a permission request or resumes a pause. K2 with identical body remains a new intent. A second service instance can lose the admission or dispatch CAS and must only read the durable record, never dispatch again.

Production schema generation and migration/replay verification belong to the data author. Consumer tests create this target fixture explicitly; passing them does not mean any deployed schema contains the table. Integration must install the real migration before enabling the keyed consumer. The existing no-key path keeps its dispatch/queue semantics, with an added generation CAS for reopen.
