# 项目管理完整交互原型：返工要求

日期：2026-11-04。状态：设计任务，不授权业务实现。依据：[记录链评审稿 D0.1](2026-11-04-project-record-chain-review.md)与[统一项目管理计划](2026-11-04-unified-project-management.md)。

## 最新范围：先交付退款链六页原型

2026-11-04 本轮范围收敛：先制作退款需求这条链的六个主页面，能点击连续走通，由用户评审后再改业务代码。下文广义页面清单是信息覆盖要求，不再要求新增十一个主路由；其他详情合并为页内标签或抽屉。

| 主页面 | 包含内容 | 主跳转 |
| --- | --- | --- |
| S1 项目概览 | 咖啡亭目标、退款里程碑、范围进度、下一步、群/需求/交付入口；新建项目可用演示弹窗承载 | 进入群讨论、退款需求、执行与交付 |
| S2 群聊与来源 | 关联项目卡、退款原消息、讨论话题、整理需求、业务待决/交付卡；关联设置抽屉 | 原消息到S3，决定回S3，交付卡到S6 |
| S3 需求与决定 | 退款范围、规则、设计摘要、AC、修订、业务决定详情与影响 | 回S2定位来源；纳入计划到S4 |
| S4 计划与执行 | 版本范围、依赖/并发、工作看板、任务包抽屉、执行模型责任与尝试详情 | 回S3标准；交付候选到S5；执行详情返回原工作项 |
| S5 候选与验收 | 候选A失败、候选B修复与复验、固定版本证据、缺陷与返工 | 失败回S4原工作项；标准回S3对应修订；通过到S6 |
| S6 交付与反馈 | 发布前后状态、环境和回退、使用入口演示、群交付卡、缺陷/新需求分流 | 交付卡回S2；缺陷回S5/工作项；新范围回S3草稿 |

六个页面均须有稳定截图与实际可点击导航。最短评审路线为S1→S2→S3→S4→S5→S6→S2；还要验证A/B版本切换、返工回原工作项和返回保留上下文。避免为广义多项目架构延迟本次六页交付。

### 主线补充：从群聊内创建项目开始

默认首次评审场景改为S2“尚未关联项目”的群聊。必须可点击“创建项目并关联”，进入原型弹窗填写名称、目标、协调负责人及可选资料/目录，校验后在同一示例状态中创建项目并关联当前群。保存成功回到群，显示项目卡，既有消息仍在；点击项目卡进入S1，再返回原群和原消息。创建/关联本身不启动模型或执行工作。

随后从退款原消息整理需求到S3，决定与范围就绪后纳入S4，交候选到S5，保留验收失败返工和B复验通过，再进入S6交付，群内交付卡返回S2，反馈能回对应需求。主评审路线为S2未关联→创建并关联弹窗→S2已关联→S1→S2来源→S3→S4→S5→S6→S2；取消/重试不重复创建示例项目，跨页名称/关联/状态一致。

每页必须有可展开“设计标注”，说明参考现有页面、实际存在的组件路径、视觉/行为沿用部分、调整部分与全新业务内容。没有对应现成页面时明确写“新增页面，沿用现有布局/组件”，不得虚构已有项目需求/验收页面。标注是评审工具，不算正式产品常驻内容；六张干净主图之外可补标注展开图。映射须由作者核对源码后给出，不能只有一份脱离页面的总清单。

### 现有 Cindy 界面基线（本轮补充）

原型必须在当前 Cindy 已有界面上补充调整。以真实客户端截图、当前组件和权威设计规范共同作为依据，不能只取灰色配色而重新设计成另一套独立管理系统。

- 保留现有窗口框架、侧栏层级、伙伴/任务入口、账号区域及导航习惯；项目入口的新增或调整位置须明确展示，不悄悄替换现有语义不同的入口。
- 群聊场景复用现有消息流、话题、消息操作和群设置结构；项目卡与关联操作作为增量放入。
- 执行任务仍沿用现有原生任务体验；原型中的模拟任务详情必须体现与工作项的往返关系，不另建聊天系统。
- 项目页面、详情抽屉和表单沿用当前组件、字体、间距、按钮、焦点和浅深主题规则；新增关系和信息层级应融入既有框架。
- 原型演示阶段/重置等控制与产品页面分离，不能当作 Cindy 新增常驻工具栏。
- 交付附简短“复用／新增／调整”说明，并注明参考的实际页面/组件。已有原型只修正偏离基线的部分，不推倒重做有效记录链。

## 产品判断

当前 project-overview-pilot 是目录下普通任务的观察入口。其真实客户端主路径、截图及有限独立验收已完成，但没有表达完整项目管理需求；不得以该试点截图作为完整项目管理设计交付或设计认可依据。

缺失的核心是新建/接入项目、目标与计划、需求与业务决定、群聊关联、工作项和上下文、执行责任与模型分档、候选版本、独立验收、发布及反馈的连续关系。此次设计返工保留既有技术证据与候选包，不继续给旧观察页增加装饰冒充产品完成。

## 交付范围

产出一个可打开、可点击浏览的独立设计原型，以及直接可查看的 PNG 页面图。所有页面使用同一套示例记录，明确标注“设计原型 / 示例数据 / 不执行真实操作”。原型仅为设计文件，不能接入宿主、账户、仓库 API 或执行任务。

设计源与图片存本地设计交付目录；仓库只保存去个人化设计说明、评审映射及决定。禁止修改业务源码、插件候选、manifest、安装/授权状态和当前运行实例。

## 原型主故事与一致性

采用“群提出退款 → 产品澄清 → 业务决定 → 纳入计划 → 拆解 → 接口/页面并发 → 候选 A 验收失败 → 原作者修复 → 候选 B 复验 → 发布 → 群内使用反馈”。规则均标示为演示假设。

可以提供与产品页面分离的“原型演示阶段”控件，切换需求提出、并发执行、返工、待交付、已交付等场景。各场景的项目统计、工作状态、候选、验收和下一步必须一致；不能同屏声称已经发布且仍等待相同版本初次验收。

共享来源与数据必须一致：同一需求/工作项/任务/候选/验收从不同入口打开同一记录。验收 A 不得跳到候选 B；已解决决定不得继续阻塞当前版本。所有稳定编号只作为示例，不冒充真实任务 ID。

允许首版一个群关联一个默认项目；自动推进程度仍是待决定产品规则，在原型中明确为示例配置，不能以用户未答复的选项作为已确定设计。

## 视觉与交互要求

- 使用 Cindy 现有设计规范；设计作者先读 DESIGN、相关设计治理与任务术语规则。项目首屏围绕目标、下一步、责任、证据组织，避免把 API 范围警告堆成主要内容。
- 桌面有真实的侧栏/页头/正文/关系区层级；窄屏成为单列且关键操作可达。浅深主题均有可查看页面，不用单一主题硬编码冒充适配。
- 主操作随状态变化。每个按钮/链接必须有明确导航、演示动作或不可用原因，不允许只有“进入→”文本没有响应。不能把所有按钮接到同一说明弹窗。
- 导航与返回保留项目、筛选和所看版本。示例创建、关联和决定只能改变原型内示例状态，刷新重置规则明确；不调用真实服务。
- 高级技术信息在详情展开：执行模型、目录、版本指纹不抢占项目首屏。
- 至少表达无项目/新项目、加载、待决、受阻、版本冲突、执行结果未知、验收失败/复验、发布与通知失败的关键恢复路径；原型场景控制与实际产品操作区分开。
- 本次不生成伪“真实客户端截图”；所有设计图图注明确标为设计原型。现有真实试点截图继续作为技术历史证据。

## 设计验收

1. 从首页创建示例项目后能进入其概览，不要求先发模型消息。
2. 从群消息进入退款需求，经计划和执行到验收/交付，再返回原讨论，链路无断点。
3. 在验收页面能辨认受验版本与当前版本，失败/修复历史不被覆盖。
4. 多项目、项目与群、业务工作项与原生任务的区别可从页面理解，不靠长篇说明补救。
5. 项目列表、概览、需求、计划/看板、群关联和验收/交付提供稳定 PNG 设计图；交互原型 HTML 作为可浏览附件。
6. 作者自查导航、数据一致性、窄屏、主题和关键状态，列出未覆盖；独立质量对照记录链评审，不修改作者设计文件。

交付附研发标准对照：现有组件/设计依据、页面复用与新增映射、标准流程与权限边界、真实可点击路径的检查结果、浅深/窄屏/键盘证据、准确原型版本及截图对应关系。原型独立 HTML 中的样式模拟不等于正式复用了宿主组件，须区分“视觉与行为沿用”和“将来实现可复用的组件”。不以文档检查或截图存在代替设计验收。主页面提供干净截图，另附复用/调整/新增图例或对照清单，标注不遮挡正常评审。

只有设计评审通过、范围冻结后再拆实现任务。本任务不把“能打开原型”算作实际项目管理已实现，不提交、推送、发布或变更现有插件。
