# Cindy 统一项目管理与多 Agent 并发迭代计划

日期：2026-11-04。状态：研究与设计提案，未实施，不是现行产品规则或发布承诺。

## 1. 结论与范围

Cindy 已有项目目录归属、普通任务、伙伴待办与跟进、群分工、Orca 多 Agent 执行等基础。当前检查的源码和接口文档，尚不足以证明已有完整的“统一需求—项目计划—依赖调度—独立验收—版本交付”体系。项目任务运行状态也不能直接代表业务进度。

建议建立 Cindy 内统一的项目管理功能：统一数据、状态语义、执行合同与交付证据；从既有项目提取内容与流程，经过映射核对后迁移。各项目的业务要求、验收标准和工程约束保留为项目数据，不各自维护一套生命周期。

工程方向为项目管理插件、版本化流程 Skill、现有宿主执行能力的组合。插件是实现边界，用户使用时仍在 Cindy 内完成项目管理。仅当真实联调证明缺少通用能力时，再补充宿主接口；不另建模型执行器，不要求安装 Paperclip 服务。群作为沟通入口，不作为项目身份或执行队列。

首个完整交付目标：两个项目同时推进，同一项目两个独立工作项并发；其中一个阻塞时，其他就绪工作继续；结果能追溯到需求、执行任务、代码版本及独立验证。

## 4. 从 Paperclip 借鉴什么

参考版本索引：Paperclip master `cb75c9510c06900411b52573696b3d03c03ac63c`；本次为官方文档与源码索引研究，未安装实跑。

| 参考设计 | Cindy 的采用方式 |
| --- | --- |
| 项目连接目标、具体工作和执行空间 | 项目有稳定身份，可关联多个仓库；执行目录与项目身份分离 |
| 工作项父子关系、依赖与原子领取 | 工作项有确定负责人、依赖条件和持久领取记录；并发不能重复领取 |
| 运行与业务状态分离 | Session/Run 完成只产生候选成果，验收结果决定业务状态 |
| 事件触发、可配置并发 | 有新增工作或状态变化再协调；避免定时唤醒模型空转 |
| 成果、审查、预算可观察 | 交付版本可追溯，实际用量与估计分开，缺失费用显示未知 |

参考：[Projects](https://docs.paperclip.ing/guides/projects-workflow/projects/)、[Issues](https://docs.paperclip.ing/guides/day-to-day/issues/)、[Heartbeats and Routines](https://docs.paperclip.ing/guides/projects-workflow/routines/)、[Dashboard API](https://docs.paperclip.ing/reference/api/dashboard/)。其中 Projects 明确不维护一个单独的项目完成百分比；Issues 的原子 checkout 能防止重复执行；Routines 默认不打开定时心跳。这些设计适合解决本次需求。

Paperclip 的[路线图](https://github.com/paperclipai/paperclip/blob/master/ROADMAP.md)区分默认分支已实现、实验性与计划中能力，且不承诺交付时间。自动组织学习、自组织等不能当成现成能力复制。Cindy 保留伙伴身份、多引擎和用户本地工作方式；不强制引入公司、CEO、雇佣层级，也不让所有项目经过单一对话串行执行。

## 5. 统一项目模型

建议业务模型如下，术语是提案；正式界面需按仓库术语流程确认，现有 Session 继续面向用户称为“任务”。

| 对象 | 必要数据与关系 |
| --- | --- |
| 项目 Project | 稳定 ID、名称、目标、负责人、优先级、仓库绑定、业务约束、流程版本 |
| 里程碑 Milestone | 本次范围、目标日期、必需验收条件、范围版本；日期可未知 |
| 需求 Requirement | 来源、用户问题、验收条件、优先级、需求修订、未决事项 |
| 工作项 WorkItem | 可交付切片、需求关联、依赖、允许修改范围、执行负责人、独立审查者 |
| 执行 Execution | WorkItem、Session、Run/attempt、实际模型、设备、目录、分支、代码基线、回执 |
| 证据 Evidence | 需求修订、代码/成果版本、验证环境、方法、结果、核验者、时间与可打开引用 |
| 交付 Release | 组成工作项、集成版本、适用验收、业务接受、打包/部署/安装结果 |
| 变更与决定 | 变更前后修订、原因、来源、影响范围；业务决定与操作授权分开 |

项目 ID 不随目录重命名变化；每个仓库有自己的绑定，跨设备路径是映射，不作为全局身份。一个工作项可以多次执行，但同一执行尝试只有一个有效持有者。一个需求可由多个工作项实现，不能通过拆成很多小项制造虚假进度。

统一主流程：收集 → 澄清 → 就绪 → 执行 → 审查 → 验收通过。取消单独记录。

- 就绪要求：目标、必要输入、验收条件、写入范围和依赖足够明确；普通技术任务不额外等待业务审批。
- 阻塞是附加状态，记录原因、影响依赖、解除条件及原阶段；一个阻塞不冻结整个项目。
- 审查不通过回到执行，保留原证据和失败原因。
- 技术验证、业务接受、集成、发布分别记录。不是每项技术修复都要求人手工接受；需要业务判断的事项才由有权决定的人处理。
- 需求或代码改变时，标出受影响证据失效范围；不能让旧版本的通过覆盖新版本。

进度首先显示各状态数量、阻塞、待决定事项、已接受范围及最近证据。若显示“验收通过 6/10”，必须明确这是某个固定范围版本内的工作项数量，不表示完成了 60% 的工时；新增和取消范围另外显示。缺少估时与历史数据时不生成精确完工日期。

## 6. 从旧项目提取并切换

统一需要迁移权威来源，不能长期让仓库任务卡和 Cindy 台账双向随意改状态。

1. **发现与快照**：读取项目入口、需求、计划、任务卡、代码状态、测试及交付记录；记录来源路径、原 ID、修订或内容摘要和扫描范围。没有扫描到的内容标为未知。
2. **结构化提取**：规则解析确定字段；模型负责理解和候选映射。区分原文事实、推断、冲突和缺失，不让模型直接决定已验收。
3. **映射**：旧项目名称、任务 ID、状态、负责人、依赖映射到标准对象。保留原 ID 别名和来源链接；子项目台账不能冒充整个项目。
4. **干跑核对**：输出拟导入清单、数量、状态差异、冲突与无法识别内容。重复导入同一来源不新增重复记录；内容变化产生差异，而不是覆盖新状态。
5. **小范围影子验证**：选一个明确范围，旧账本仍是权威，Cindy 只演算与展示；这一阶段明确标为影子数据，不向同一事项重复派工。
6. **单次切换**：范围核对完成后，先核实在途旧任务与写入者，记录切换点，再让 Cindy 成为该范围的唯一状态写入入口。旧入口改为来源档案或生成的只读视图。
7. **持续使用与回退**：保留迁移版本、事件记录和导出；失败时恢复权威来源前先处理在途执行，不能仅恢复数据库后重新派发已经执行的工作。

试点约束：咖啡项目已有部分子范围的结构化台账，导入时明确范围；token 类多仓库项目需保留旧任务 ID、实际仓库映射及共享迁移串行约束。原工程规则中的安全、数据和发布约束保留；被统一替换的是管理方式，不是业务事实。与新流程冲突的旧写入规则，必须在切换时同步调整，不能悄悄忽略。

导入的“已完成”先保留为历史声明；只有证据与当前验收条件匹配才转为验收通过。资料导入和任务执行分离，点击导入不自动开始所有积压工作。

## 7. 并发执行设计

Cindy 负责组合优先级、拆解与协调；每个项目的上下文、执行和状态独立。长期伙伴承担专业责任，执行任务按工作量展开，不能因为只有一个研发岗位就全局串行。

调度输入为就绪工作项、依赖、项目优先级、已获授权、机器状态、模型额度、预算及共享资源。业务选择由 Agent 作出，宿主只保证原子领取、权限、停止和真实资源约束，不写死所有用户最多运行几个 Agent。

派发顺序：选择就绪项 → 原子领取并记录修订 → 确定工作目录与代码基线 → 以稳定 requestKey 创建/发送 → 保存原生回执 → 按原回执观察 → 候选成果进入独立验证。派发意图先持久化；超时或 ACK 不明时查询旧记录，不更换键重发。

并发规则：

- 跨项目默认可并发；同项目无依赖且写域独立的功能可并发。
- 代码写入使用独立 worktree；共享接口先确定契约；Git 隔离不能解决共享数据库、端口、部署环境和迁移顺序冲突，这些资源单独领取。
- 调度考虑等待时长，避免大项目长期占满所有资源；优先级变化有记录。
- 收到停止立即禁止新派发，区分停止请求、引擎实际停止和子任务已收敛；租约过期不证明旧执行已停止。
- 旧持有者迟到回报不得覆盖新修订；重启恢复先对账再决定恢复执行。
- 实现者自测之后，由独立执行上下文验证；质量任务读明确版本，发现问题返回对应工作项。
- 发布集成只汇合本次范围必需工作，不等待项目全部积压项。

协调触发优先来自真实事件；当前插件没有完整任务事件订阅时，可用有界、带退避的回执查询，查询本身不唤醒模型。插件面板关闭后的执行、重启续接和远端能力必须真实验证；不把页面内计时器当作可靠后台调度器。

## 8. 在 Cindy 中如何实现

| 层 | 职责 | 边界 |
| --- | --- | --- |
| 项目管理插件 | 项目列表、需求/里程碑、迁移、依赖、业务状态、证据、总览 | 通过公开接口读写；不直连宿主私有数据库或 IPC |
| 版本化流程 Skill | 提取、拆分、就绪判断、交接、独立验收的工作方法 | 不作为唯一状态存储；不自行修改个人身份或系统提示词 |
| Cindy 宿主 | 原生任务、Orca、模型、权限、工作区、停止、持久执行回执 | 只补通用缺口；复用现有运行时与权限机制 |
| 持久项目数据 | 使用插件 Library 等受支持存储，保存修订及导出 | 先验证事务能力与生命周期；不靠个人聊天历史维持唯一状态 |

建议先采用单一协调主机负责写入，其他客户端通过支持的宿主入口查看或请求变更。多设备主从切换是后续专门验收项；不能靠同步 SQLite 文件实现多主写入。

代码全部归属本 Cindy 仓库，隔离开发使用本仓 worktree。插件源码目录按本仓打包约定在第一阶段确定，不能把 Bot 的临时 workspace 当作客户端实现目录。需要补宿主时，优先核对 `pluginTaskService.ts`、`pluginTaskStore.ts`、`sessionExecutionOwnership.ts`、`pluginObserveTasks.ts` 与现有插件协议；不要先增加另一套项目执行器。

## 9. 分阶段迭代与退出条件

阶段按依赖推进，不承诺未经估算的日历日期。每阶段结束根据实际耗时、风险与版本重新估算下一阶段。

| 阶段 | 具体工作与交付 | 必须通过的退出条件 |
| --- | --- | --- |
| M0 能力与合同基线 | 核对安装版/源码/插件版本；真实探测 tasks、observe、Orca、存储、关闭面板后的生命周期；冻结最小字段、状态和执行合同 | 每项能力有真实回执或明确缺口；确定可行执行路径；无私有接口绕行 |
| M1 标准数据与导入 | 项目/需求/工作项/证据最小模型；导入干跑；双项目只读总览；迁移差异报告 | 两项目样本可追溯；重复导入零重复；冲突和未知可见；重开数据不丢 |
| M2 最小并发闭环 | 领取、派发、隔离执行、回执观察、独立验证；项目总览连到原生任务 | 两项目同时真实执行；一项目两项并发；阻塞一项其余继续；每项有确定版本与结果 |
| M3 交付闭环与正式切换 | 集成检查、范围变更、证据失效、验收与发布分层；按范围迁移权威来源 | 旧通过不能覆盖新版本；切换后单一状态来源；从需求能打开最终成果；实际交付状态准确 |
| M4 可靠运行与安装验证 | 重启对账、关闭面板、停止、撤权、离线与恢复；兼容升级；适用远端/手机路径 | 中断不重复执行、不误报完成；旧版本缺能力有明确恢复办法；打包与安装版实跑均留证 |
| M5 数据驱动改进 | 分析等待、返工、人工介入、成本和交付周期；对拆分与调度策略作版本化小范围实验 | 同类范围比较有数据；质量不退化；可回退；达到收益才扩展，不自动扩权 |

M0 发现阻塞执行的基础缺口时，先实现最小通用修复，再进入 M2；不把核心可靠性缺口包装成插件已可无人值守。M2 是早期主验收，不推迟到复杂报表、甘特图或自动学习完成后。

产品与体验负责标准流程和页面状态；研发负责合同、存储和执行连接；质量在实现前形成反例、在实现后独立验证；Cindy 负责范围与证据统筹。角色是责任，具体执行可并行展开；本计划不表示已经派发这些任务。

最小页面：项目总览、项目详情、工作项详情、待处理事项、导入核对。每页优先回答“现在做什么、卡在哪里、依据是什么、下一步由谁处理”，高级执行参数渐进展示。初版不建设组织市场、自动招募、复杂财务核算或无限可配置流程编辑器。

## 10. 验收场景

| 场景 | 期望结果 |
| --- | --- |
| 两项目含同名工作项 | 项目 ID 隔离，输入、成果及证据不串项目 |
| 多仓库与 worktree | 执行落在正确仓库，项目归属不随 worktree 分裂 |
| 同一来源重复导入 | 保持同一记录；来源变化可见，不覆盖较新的业务状态 |
| 旧账本声称完成但无证据 | 保留历史声明，不自动验收通过 |
| 两执行者抢同一工作项 | 仅一个有效领取者；失败者不派发 |
| 派发后响应丢失 | 查询原 requestKey，不创建第二个执行 |
| 一个依赖受阻 | 仅依赖它的项等待，其他项继续 |
| 独立 worktree 共用数据库迁移 | 共享迁移按约束串行，其他写域可并发 |
| 执行完成但验证失败 | 进入返工，不计算验收通过 |
| 验收后需求或代码改变 | 标记受影响证据需重新验证 |
| 重启、面板关闭、掉线 | 回读真实回执；未知不报成功，不凭租约超时重派 |
| 停止时仍有 Worker | 显示实际未收敛状态，不只根据 Lead 停止判定全部停止 |
| 撤权或账号切换 | 后续操作遵循现有宿主边界，不从另一入口重试绕过 |
| 无费用数据 | 显示未知，session-total 不重复分摊成逐项精确费用 |
| 手机、窄屏、双主题 | 主流程可读可用；不支持的操作明确反馈，不假装远程执行成功 |
| 安装与升级 | 安装版版本匹配；项目数据保留；旧插件的权限和配置不丢 |

用实际生产入口验证用户可观察结果，避免仅测试硬编码状态映射。根据变更风险选择自动测试、真实模型执行和界面验收；模型费用、环境与权限使用现有约束。

## 11. 自我迭代方法与发布

自我迭代指基于交付证据改进产品和流程，不是 Agent 自行修改自己的身份、扩大授权或把每次失败永久写成规则。

每轮记录：就绪到开始的等待时间、开始到验收的周期、首次验证通过率、返工次数、阻塞原因、每项实际用量、人工介入原因。运行数量增加不自动算效率提升；以相近范围、复杂度和质量条件比较。缺失数据单列，不补零。

改进循环：收集失败样本 → 找到具体原因 → 提出小范围改动 → 版本化代码/流程与回归样本 → 在一个范围验证 → 对比质量和效率 → 保留或回退。成功后再扩大适用范围；模型与策略版本要可追溯。尚未实测前不承诺某个吞吐提升比例。

发布按现有仓库开发与更新流程进行：定向测试、类型检查、独立审查、版本集成、打包、安装版验证。`release:package` 仅表示打包入口，不等于发布或安装成功。插件与宿主建立最低能力版本契约；新增能力沿用宿主正常授权，已有批准与数据要兼容迁移。

第一版完成的判据是“导入两项目 + 真实并发 + 独立验收 + 可恢复 + 安装版可用”。漂亮的看板、生成计划、运行结束或打包成功，均只能算其中一个环节。
